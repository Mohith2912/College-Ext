# Authentication boundary

Both Next.js applications call `makeAuth("users")` or `makeAuth("admin")` and export the returned `handlers`, `auth`, `signIn` and `signOut`. Their HttpOnly, SameSite=Lax session and CSRF cookies use different names; HTTPS deployments add the Secure attribute. Auth.js handles its own sign-in and sign-out CSRF checks. Custom mutation routes must call `assertTrustedOrigin` and `parseJsonRequest` before performing work.

Credentials sessions deliberately use Auth.js encrypted JWTs because the credentials provider does not support its normal database-session flow. The token contains user identity, app surface and `sessionVersion`, never authoritative role claims. Every session read looks up the current user, verification, session version and membership. Every protected service also checks current organization membership and required roles. Deleting/revoking membership or changing roles takes effect on the next request. Incrementing `sessionVersion` revokes all existing sessions. Do not use the auth package from edge middleware; it requires the Node runtime and database.

`requireUser(auth)` authenticates a verified, undeleted account. `requireOrganizationMembership(auth)` returns `{ user, organization, membership }` in the configured organization. `requireRole`, `requireAdminAccess`, `requireContentEditAccess` and `requireReviewAccess` enforce current role membership. Super administrators do not bypass tenant boundaries. Resolve resources under the returned organization ID; never use organization IDs from a request body. `requireOwnership` checks private resource owners. `requireVerifiedStudent` requires an approved, unrevoked institutional verification with a future expiry; a role label alone is insufficient.

Registration validates explicit terms consent and creates only a STUDENT membership. It stores a 256-bit email token's SHA-256 digest, delivers the original through SMTP, and refuses to report delivery success if SMTP rejects the message. Verification atomically claims its token, verifies the account and deletes outstanding verification tokens. Repeating registration for an unverified address re-sends verification without replacing its original password. Verification links display a confirmation form; the consuming action is POST so email scanners cannot activate accounts by following a GET link.

Set `DATABASE_URL` to a MySQL connection, `AUTH_SECRET` to at least 32 random characters, `USERS_URL`, `ADMIN_URL`, and `ORGANIZATION_SLUG`. Production URLs must use HTTPS. Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, and optional `SMTP_USER` / `SMTP_PASSWORD`. `SMTP_SECURE=true` uses implicit TLS; production without implicit TLS requires STARTTLS. Development defaults to the local SMTP listener at 127.0.0.1:1025. Credentials never appear in client bundles or error responses. Lazy runtime validation permits builds without real secrets but rejects requests if runtime configuration is missing.

Rate limiting uses atomic, persistent MySQL counters in fixed time windows across both application replicas. `TRUST_PROXY=true` is appropriate only behind an ingress that removes and rewrites incoming forwarded headers; otherwise all requests share a conservative network bucket and separate normalized email buckets. Run `pruneRateLimits()` as scheduled maintenance to remove windows older than one day. A database failure prevents authentication; it never bypasses rate limiting.

The first batch does not yet provide password reset, MFA, institutional-email issuance, or transcript retrieval. Deploy account recovery before opening general registration to real users. Production email delivery uses a configured SMTP service; there is no console-token bypass.
